# 保持功能与 UI 的渐进式代码优化方案

日期：2026-09-18。状态：**阶段 0–1 已按限定范围实施并验证，阶段 2–7 尚未实施**。详见[阶段 0–1 实施记录](./code-optimization-phase-0-1-2026-09-18.md)。依据：[代码体积与结构审计](./archive/code-bloat-audit-2026-09-18.md)。

目标是减少无效代码、重复实现和模块耦合，改善首页加载，同时保持当前功能、外观和交互。每次只处理一个明确边界，通过验证后再进入下一批。

审计基线为 `8f3b9e8ae711`。当前工作区还有其他窗口正在修改模型、视频、热力图和语言文件；原审计行数、诊断数量、包体数字只作为参考，实施前重新采样，不将其他窗口的改动归入优化成果。

## 执行约束

- 保持页面布局、文案、颜色、尺寸、间距、响应式断点、hover、焦点和动画效果。弹窗继续沿用 AppModal。
- 结构搬迁尽量原样保留 JSX、className、props、状态归属和 API 请求契约。移动代码、改变逻辑、改变加载方式分别交付。
- 保留登录竞态保护、账号与企业隔离、权限判定、请求取消、幂等建单、支付恢复和必要兼容。现有测试、类型与翻译不以减少行数为理由删除。
- 每批开始记录涉及文件的当前内容和差异；文件出现新的并发修改时重新核对，必要时先做无冲突的批次。不覆盖、暂存或回退其他窗口的工作。
- 每个子批次形成独立可审查补丁；需要回退时只撤销该补丁。共享文件已有后续修改时手工合并回退，不执行整仓 reset / checkout。
- 每批仅格式化本批文件，避免全仓格式化和无关重命名。新增必要中文注释，沿用现有风格、组件和工具。
- 临时构建、截图、日志和一次性脚本放仓库外的任务专属目录；有长期价值的行为测试放现有测试目录。

## 总体顺序

| 阶段 | 内容                                | 相对风险   | 阶段完成标准                               |
| ---- | ----------------------------------- | ---------- | ------------------------------------------ |
| 0    | 建立当前功能、UI、测试和包体基线    | 无产品改动 | 后续差异有明确对照，已有失败单独记录       |
| 1    | 清理确认无用代码与直接依赖          | 低         | 每项有无引用证据，现有功能与高亮正常       |
| 2    | 支付弹窗按需加载                    | 中         | 购买全过程不变，首屏体积门禁恢复通过       |
| 3    | 合并行为相同的局部重复              | 低至中     | 请求参数、分页结果和错误语义不变           |
| 4    | 逐块拆分 `common.tsx`               | 中         | 职责独立、已发现依赖环消除、状态与外观不变 |
| 5    | 拆分密钥页、充值和企业页            | 中         | 页面变薄，表单、权限、支付与企业流程不变   |
| 6    | 分功能整理全局 CSS                  | 较高       | 无无法解释的视觉差异，样式归属清晰         |
| 7    | 按语言加载 i18n，必要时再按业务拆分 | 较高       | 中英文直达与切换正常，无闪烁、缺词或裸 key |

阶段 0、1 作为第一轮实施范围。阶段 2 独立交付；阶段 3、4、5 再逐个推进。阶段 6、7 在前面稳定后进行，每次只动一个功能区域。阶段号表示建议顺序，不表示一次性重构整个阶段。

## 阶段 0：建立可比较的基线

1. 记录 HEAD、工作区差异、运行时版本及本轮准备修改的文件，明确其他窗口正在使用的文件。
2. 在项目声明的 Node / npm 环境执行类型检查、现有全量测试和隔离生产打包；运行现有体积与静态发布完整性检查。构建产物不覆盖其他窗口使用的 `dist`。
3. 记录真实失败及原因，不为得到绿色结果删测试、降低覆盖率或提高体积预算。旧审计的首页 JS 为 440.9 KiB gzip，已超过 440 KiB 预算；必须先确认当前版本是否仍然如此。
4. 采用固定测试数据、账号与企业上下文，为本批涉及的页面保存基线。阶段 0 先覆盖首批所需页面，后续批次开始前补充对应基线，不要求先为所有产品状态建立庞大截图库。

UI 基本矩阵：浅色 / 深色 × 中文 / 英文 × 桌面 / 手机。建议固定桌面 1440×900、手机 390×844；涉及断点时再检查断点两侧。截图需保持同一数据、字体、视口和滚动位置；时间、二维码等动态内容使用固定数据，避免任意扩大忽略区域。

基线包含外观和行为：表单输入、切换、滚动、弹窗打开与关闭、键盘焦点、加载 / 空数据 / 错误状态。涉及付款、密钥或企业写操作的验证使用隔离数据和模拟接口，避免对真实业务产生副作用。

**通过条件：** 知道“优化前是什么样”；已有问题与新增问题可区分。此阶段不顺带修复无关问题。

## 阶段 1：先做有确切证据的清理

按以下四个子批次分别执行：

| 子批次 | 改动范围                                       | 保护与验证                                                                        |
| ------ | ---------------------------------------------- | --------------------------------------------------------------------------------- |
| 1A     | 未使用导入、私有工具和企业页旧示例数据         | 重新核对 TypeScript 诊断；删除变量前检查初始化表达式、hook 和模块导入是否有副作用 |
| 1B     | 企业页不可达的旧 `member` 表单及专属提交函数   | 保留真实邀请、加入审批、规则设置、部门 CRUD；跑企业成员与邀请相关测试             |
| 1C     | 审计确认的 3 个无生产入口模块及专属测试 / 样式 | 再查静态、动态、构建注入和字符串入口；仅删除完全专属代码，相关页面做视觉抽查      |
| 1D     | `prismjs` 直接依赖及相应锁文件条目             | 单独更新依赖，不升级其他库；验证文档与代码高亮、依赖安装和生产打包                |

1C 的候选是 `analytics-time-range-picker.tsx`、`trae-usage-department-table.tsx`、`utils/invitation.ts`。旧时间选择器的全局 CSS 只有在类名与动态用法均确认专属时才清理；不能把它当成批量 CSS 去重的入口。

**完成标准：** 删除范围有引用证据，对应现有测试通过，无新增可见变化。生产 JS 原已不含这些旧模块，不以首页 JS 必须下降作为本阶段验收条件。`prismjs` 的收益也是依赖维护简化。

## 阶段 2：独立实施支付弹窗按需加载

主要边界：`src/components/header-purchase.tsx` 与现有支付弹窗模块。

1. 首先明确加载边界，保持套餐目录预加载、购买意图恢复和支付 hooks 的现有行为。只在准备进入支付流程时加载相关模块，不借机修改支付业务。
2. 沿用现有弹窗和加载样式，保持用户操作有反馈。防止局部加载触发外层 Suspense，导致整页或底层套餐弹窗消失。
3. 校验冷缓存、慢网、模块加载失败和重复点击。失败可使用现有错误提示与重试交互，不新增一套弹窗、不让选择状态丢失。
4. 保留 `PurchasePaymentContent` 的 `closing → AppModal.afterClose → onClose` 顺序。不能因为父级条件渲染提前卸载，截断退出动画、清理流程或滚动恢复。
5. 加载未完成时切换账号、企业、套餐或离开页面，迟到的模块加载结果不得创建旧主体订单。未同意协议前仍不得建单。

**验收：** 未登录选套餐 → 登录后续购；个人 / 企业切换；实名门禁；同意协议；建单 / 丢失响应恢复；切渠道；查单；付款与关单竞争；退出动画；焦点和滚动位置。请求次数不能出现重复建单、重复查单或多次成功提示。

旧审计中仅改变加载入口的构建对照减少了 24.3 KiB gzip。这是方向性证据，正式实现以新基线实测为准，不直接复制诊断用的空白 fallback。目标是首页 JS 回到现有 440 KiB 预算内，其他预算不放宽。

## 阶段 3：只收敛已确认行为相同的重复

3A：先合并 `src/api/user-api-keys.ts` 的个人 / 企业全量分页循环，保留两个公开业务函数，在本文件内复用分页辅助函数。

验收包含：单页、多页、缺省分页信息、重复页、ID 去重、100 页上限、模型选项合并、请求取消及失败。不得改用其他模块的严格分页工具，因为重复页与截断的处理语义不同。

3B：在密钥页中抽取共享的请求参数转换与限制映射；纯转换先独立，Toast、字段错误和提交时机继续由原页面控制。保留空值与未修改值的差别。

**完成标准：** 输入相同，输出与副作用相同；业务入口仍清楚，没有为几十行重复建立全项目通用框架。仅为现有测试未覆盖的实质行为边界补测试。

## 阶段 4：分四步拆分 `common.tsx`

| 子批次 | 拆分目标                                             | 验收重点                                                                   |
| ------ | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| 4A     | 客服事件、未读计数等轻量通信工具                     | 全站客服入口可用，通信缓存保持单实例，迟到通知不覆盖新状态                 |
| 4B     | PageTitle、ModelCard 等展示组件                      | 原 JSX / className / 文案不变，props、事件和主题显示相同                   |
| 4C     | 登录面板与弹窗整体迁移，再分别处理账户设置和客服组件 | 登录竞态、购买意图恢复、验证码计时、资料更新通知、客服草稿、关闭与重开行为 |
| 4D     | 公共 / 控制台布局与导航                              | 路由直达、权限、语言路径、切换账号、通知及草稿保护                         |

每一步先搬迁再更新调用入口，必要时短期保留兼容导出；新模块不能再从 `common.tsx` 导入刚迁出的功能。兼容导出的清理单独核对，不要求一次改完所有调用文件。

特别检查组件身份：新组件定义放在模块级，保持 key、条件渲染、Portal 容器和状态归属。拆分本身不得让父组件每次渲染都重建子组件，导致输入、焦点、倒计时或未提交表单被重置。副作用的依赖、ref 生命周期和清理时机必须保持原义；区分可见状态与挂载状态，不能将退出动画所需的双状态简化为条件立即卸载。

**完成标准：** 两条已确认的依赖环消除，模块职责可独立理解，原页面和登录 / 账户流程通过回归。以职责边界评价结果，不为了统一文件行数继续拆碎。

## 阶段 5：逐页整理复杂业务

5A：密钥页。先完成阶段 3B，再拆无状态列表，最后拆受控编辑弹窗。列表筛选、分页、企业上下文和操作状态先保留原有归属，单项与批量继续共用原表单，不一边移动一边重写状态管理。验证创建 / 编辑 / 删除 / 批量部分失败、IP 白名单未改与清空、订阅模型限制、关闭后清除密钥全文。

5B：充值。先将账务上下文与 `PaymentReturnNotice` 移到合理共享模块，再将 `RechargeTab` 原样迁到独立业务组件，使 `recharge.tsx` 不再依赖整个 `billing.tsx` 页面。原有账户作用域 key、订单恢复、轮询、关单及回调顺序保持不变，本批不同时改变加载方式。

5C：企业页。在旧代码清理稳定后，先拆纯部门树转换，再按独立职责拆展示块和弹窗。保留真实部门 ID、虚拟根限制、自定义角色、真实权限及版本字段，不重写真实成员和部门请求流程。

每个子批次独立回归并交付，不并行改同一个大页面。视频与模型文件当前正被其他窗口修改，不列入本计划第一轮整理范围。

## 阶段 6：按组件归属整理 CSS，始终以现有外观为准

先选择独立、引用边界明确的一块；共享登录与弹窗样式放后面。账单、密钥、首页资讯等各自作为小批次，不能一次重排整个 `styles.css`。

6A：梳理选中区域的选择器、继承、媒体查询、主题和覆盖链。把最终生效行为记录清楚；精确重复的规则也需检查是否用于恢复中间被覆盖的属性。

6B：分离归属，优先保持原有加载时机和有效覆盖顺序。分散在文件多个位置的规则不能简单一起移动，否则会改变级联；无法保持等价的部分先留在原位，后续单独处理。

6C：在 6B 的视觉验收通过后，再单独评估删除失效规则或延后加载。结构搬迁与 CSS 按需加载分别比较，检查直达路由、路由往返以及弹窗首次打开时是否出现无样式闪烁。

**验收：** 对该区域执行浅深色 / 中英文 / 桌面手机矩阵；验证悬停、聚焦、禁用、错误、展开、滚动与弹窗叠层。发现非预期差异就修正或撤回本批，不通过更新截图接受 UI 改变。保留 Semi 样式与 Portal 的正确覆盖关系。

## 阶段 7：最后处理语言加载

7A 先按当前语言加载，7B 再根据收益决定是否按公开页 / 控制台 / 企业模块拆分。两步分别验证，不同时改翻译 key、文案和路由规则。

首次加载应在现有启动流程中确保所需资源就绪；切换期间复用现有界面和加载行为。API 错误翻译、应用外调用 i18n 的工具，以及尚未挂载页面的文案依赖都必须纳入检查。

**验收：** 中文与 `/en` 首次直达、刷新、切换往返、控制台 / 企业深层路由、冷缓存慢网、加载失败恢复；不存在空白、裸 key、短暂错误语言及路由竞争。保留两种语言全部能力，不删除英文资源换取体积下降。

本阶段收益以实际包体和首次交互表现共同评价；在保持原有体验的条件未满足前，保留同步实现，前面已完成的优化可以独立保留。

## 验证与交付规则

| 变更类型                                 | 最低验证范围                                                       |
| ---------------------------------------- | ------------------------------------------------------------------ |
| 清理未使用私有项                         | 类型检查、相关现有测试、审查副作用和引用；无渲染变化不新建截图测试 |
| API / 数据转换                           | 对应接口与调用页测试；比较请求字段、错误语义、取消和边界数据       |
| 页面 / 弹窗 / 布局搬迁                   | 对应组件与页面测试、真实浏览器交互和受影响 UI 基线对比             |
| 支付加载、公共模块、依赖、全局 CSS、i18n | 定向回归后跑全量测试、类型检查、生产构建、体积与静态发布完整性检查 |

复用项目现有 `typecheck`、`test`、`size:check`、`release:verify`。隔离构建时将体积与发布检查指向同一产物目录；不要仅看到 Vite 打包成功就宣称全部通过。覆盖率检查沿用现有配置，在变更命中其覆盖模块或调整相关测试时运行，不降低门槛。

可直接复用的测试重点：

- 登录 / 公共模块：`src/components/common.test.tsx`、`src/store/auth-slice.test.ts`、`src/store/purchase-intent-slice.test.ts`、`src/components/header-purchase.test.tsx`。
- 支付 / 充值：`purchase-payment-modal`、`purchase-payment-boundaries`、`use-plan-payment`、`use-plan-payment-recovery`、`app-modal` 对应测试，以及 `src/pages/recharge*.test.tsx` 和 `billing.test.tsx`。
- 密钥：`src/api/user-api-keys.test.ts`、`src/pages/console-account.test.tsx`、`src/utils/api-key-whitelist.test.ts`。
- 企业：`trae-enterprise-members`、`trae-enterprise-department-tree`、`trae-enterprise-invitations`、`trae-enterprise-join-requests` 对应测试。

阶段 1 如果仍有已记录的原有包体超标，只能标注“未解决且未恶化”，不能写成完整构建通过；阶段 2 应恢复体积预算，之后以持续通过为要求。新增失败必须解决或撤回对应补丁后再进入下一批。

每批交付说明只包含：具体改动、维护 / 体积收益、功能与 UI 验证结果、仍存在的原有问题、回退范围。测试用例数因删除废弃组件测试而减少时说明对应关系，不能误删仍保护现有功能的测试。

## 暂缓项目

- 只有测试引用但可能存在外部消费者的旧公开 API：先核对外部契约，再独立决定退役。
- 登录 reducer 的形式性去重：收益较小，近期修复的请求归属检查优先保持稳定。
- 统一全部分页、错误处理和金额 / 时间转换：当前业务语义不同，不以代码相似为依据强行合并。
- 全面更换组件库、状态管理、图表库，或重新设计 UI：不属于本轮优化目标。

**第一轮具体交付：阶段 0 + 阶段 1 的独立子批次。** 完成后再用更新后的测试、UI 对比和包体数据进入阶段 2，逐步累积收益。
